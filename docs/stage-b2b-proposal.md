# Proposed Stage B2B — separate approval required

B2A stops at isolated policies, preview, transaction proof and synthetic performance evidence. It does not authorize integration, storage replacement, data migration, vendor selection, production provisioning, deployment or main merge.

## First: demonstrate intelligence value on a small authorized list

Approve or amend the [twenty-prospect benchmark protocol](real-world-benchmark-proposal.md). Confirm the exact manager-authorized cohort, source/research permissions, participants and approved working environment before any real data is used. Do not place real records in the new proof repository or code fixtures. Produce inspectable answers, independent accuracy review, useful verification steps, prioritization rationales and end-to-end timing. No business outreach without additional authorization.

Acceptance: no wrong-business/suite accepted associations; no unsupported verified authority or eligibility; cited/source-faithful findings; useful qualified unknowns/hypotheses; clear time/usefulness evidence. Report failures, not just aggregate accuracy. This is the next product milestone and can precede a production backend.

## In parallel only if approved: finalize policy and boundary design

- Review proposed freshness windows/source classes and the handling of old publications, representative record reviews and inference decision-risk caps.
- Approve exact/explicit/ambiguous suppression scope and who can attest expanded targets. Define organization/workspace manager delegation, review holds and signed role/scope history.
- Specify append-only conflict resolution and explicit identity acceptance events. A single candidate still requires reviewed acceptance. Ambiguous legacy records remain raw.
- Review preview reconciliation against synthetic edge cases, plus payload/graph/performance budgets. No conversion of real records.

Acceptance: agreed versioned policy, provenance/verification semantics, deterministic review behavior and no inherited restrictions through ambiguous identity.

## Backend implementation is a later explicit gate

Only after permission to select an environment: evaluate hosting/authentication/storage options against workspace isolation, real sessions, transactional constraints, optimistic revisions, audit retention and recovery. Do not select/provision a vendor under the current approval. The disposable SQLite proof is not the production relational schema.

Before real service implementation/replacement, present the normalized schema and API/access policy for review. If authorized, build a nonproduction synthetic environment first and prove real-session verification, revoked-role behavior, cross-workspace denial, typed database constraints, actual crash/restart durability, backups and restore, concurrent requests, request size limits and transport security. No offline sync initially. “Outcome unknown” and unsaved-draft recovery must be explicit.

## Integration and migration remain separate

A live interface integration requires its own approval and must preserve FieldMind's visual identity, research-first flow and existing useful functionality. Keep new facts source-backed with qualified hypotheses and uncertainty; do not expand CRM, routing, enrollment or sales scripts.

Persistence replacement needs separate approval. Existing-data migration additionally requires a concrete dry-run inventory/mapping/reconciliation, identity review, untouched source snapshot, rollback plan and explicit cutover approval. No automatic merge, silent overwrite or deletion is permitted.

Requested B2B decision: approve the bounded intelligence pilot and policy refinements, or amend them. Do not bundle that approval with live integration, vendor provisioning, persistence replacement or migration.
